# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Docker image for running Claude Code or Codex in ephemeral containers, plus the `clod` launcher (bash, kept compatible with the bash 3.2 macOS ships). Supported hosts: macOS (Colima or Docker Desktop) and Linux (rootful Docker Engine). No compose, no persistent containers - just `docker run` with `--rm`.

## Build & Run

```bash
clod          # launcher script; builds images as needed and wraps docker run
```

`Dockerfile` is the generic base image (`clod`), `FROM $BASE` with `ARG BASE=debian:trixie-slim`; another Debian or Ubuntu base (a project's devcontainer image, say) gets the same layer on top, keeping its `ENV`, starting as root whatever `USER` it ends with, failing at once without `apt-get`, and adding the NodeSource and GitHub apt repositories only where no apt source already names them (apt refuses one listed twice with different keys). A user such a base already has at claude's uid or gid keeps its name and files, and claude's `/etc/passwd` and `/etc/group` lines move ahead of its so the ids resolve to `claude`. Personal or per-stack tooling goes in variants: `~/.clod/images/<name>/Dockerfile` or, failing that, a bundled `images/<name>/Dockerfile` in this repo, built `FROM clod` (or another variant), selected with `CLOD_IMAGE=<name>` and auto-built as `clod-<name>` when its files or the image it is `FROM` change. Variants combine as `CLOD_IMAGE=a+b`: clod builds `clod-a`, then `b` with `--build-arg BASE=clod-a` as `clod-a.b`, in the order given, so every bundled variant starts `ARG BASE=clod` / `FROM $BASE` (as does `clod image new`'s starter), and clod expands ARG defaults in `FROM` lines to find what a variant builds on. A variant can also be `FROM clod-a.b`, which `clod image new NAME a+b` starts. Everything clod prints, and `$CLOD_IMAGE` in the container, names an image as `-i` does (`clod`, `a`, `a+b`, via `image_name`); the Docker names `clod-a` and `clod-a.b` appear only in `FROM` lines and Docker's own output. Variant names `image new` creates must be valid in a Docker image name: lowercase, joined by `-` or `_`. Bundled variants are examples for a language or stack; keep them generic. A variant's instructions for Claude go in a Markdown file it copies into `/etc/clod/.claude/rules/` (the bundled ones use a `CLAUDE.md` beside the `Dockerfile`); the entrypoint loads `/etc/clod` with `--add-dir=/etc/clod` and `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. It also passes `/etc/claude-code/settings.json` as `--settings`, unless the arguments have their own `--settings` (only the last one applies); Claude Code never reads that file itself, so it isn't a managed source, which an organisation's server-managed settings would replace. The base image's own instructions, describing the container to Claude, are `container.md`, copied in as `/etc/clod/.claude/rules/clod.md`. The launcher builds the base from its own (symlink-resolved) directory when `Dockerfile` changes; `entrypoint.sh`, `container.md` and `clipboard.sh` are left out of its hash, since every run mounts them read-only from that directory over the image's copies (which serve runs without clod), so changing them rebuilds neither the base nor the variants on it. The image runs the entrypoint with `sh`, as the mounted file keeps the checkout's mode.

`-i devcontainer` (or `devcontainer:NAME`, for `.devcontainer/NAME/devcontainer.json`) is the workspace's devcontainer image, and `devcontainer:PATH` (a `/` in it, or a leading `.` or `~`; relative to the current directory) one anywhere, as a project, config folder or config file, built in the folder holding its `.devcontainer` (else the config's), whatever the workspace, scratch included; it is the same image as the project's own (a named config's keeps its `NAME`), and keeps the path as its name (`$CLOD_IMAGE`, `image build`'s output). It is built by the host's `devcontainer build --workspace-folder W --config F --image-name TAG:devcontainer` (the devcontainer CLI is a host requirement for this only; the launcher parses no JSON), then the base `Dockerfile` with `--build-arg BASE=` that image and `DEVCONTAINER_METADATA=` its `devcontainer.metadata` label, which the Dockerfile reads with python3 to move `remoteUser` (else `containerUser`) to claude's ids and write `containerEnv` to `/usr/local/share/clod/devcontainer.env`, which the entrypoint exports for variables not already set. The `:devcontainer` tag is removed after. Its Docker name is `clod-devcontainer-[NAME-]HASH` (`dc_re`; `HASH` of the config's real path), labelled with its config file and workspace (`clod.devcontainer.config`, `.workspace`), from which `walk_image` checks images of other workspaces, stale when the config has gone; `image_name` shows it as `devcontainer[:NAME]` and `tag_variant` puts it in `variant_dc` as the root of a chain, so it goes first in a combination (`devcontainer+sudo`, `clod-devcontainer-HASH.sudo`). Its hash covers the files beside the config (`.devcontainer/` itself not recursively, a `.devcontainer/NAME` folder recursively, or `.devcontainer.json` alone) and `base_hash`. clod never runs `devcontainer up`, so nothing else in `devcontainer.json` (lifecycle commands, `initializeCommand`, mounts, run args, ports) is used. `CLOD_DEVCONTAINER=auto` (`off` by default) runs `devcontainer` when the workspace has a default config and the CLI is installed, unless `-i`, the shell or the `.envrc` set `CLOD_IMAGE` (`image_chosen`); without the CLI it notes it and runs the usual image. A devcontainer the workspace lacks sets `image_error`, an error only where the image is needed (`need_image`), so `clod home` and the like still work. `image new` refuses the name and `FROM` a devcontainer, `image edit` and `image rm` point at the config and `image clean`, and `clod env` names a devcontainer the run doesn't use.

`plugins/show-image` is a Claude Code plugin, copied into the image at `/etc/clod/plugins/show-image` and, like the files above, mounted read-only over that copy on every run; the entrypoint passes each `/etc/clod/plugins/*/` folder as `--plugin-dir`. It adds a `show_image` tool for the model and a `/show-image PATH` command, both drawing the picture inline with Claude Code's `Image` element, which kitty and Ghostty draw (as kitty graphics, sent as bytes: a file path would name a file on the host). A PNG of at most 2 MiB goes as it is; anything else goes through `convert.py` (Pillow, `python3-pil` in the base image), which prints the first frame as a base64 PNG, at most 1200 pixels a side and shrunk until it fits 2 MiB. The plugin keeps the last 20 pictures in `$.state` and draws them in three places: a command's `CommandOutput` row (whose `text` carries the plugin's name before the answer, `show-image: #ID PATH`), the tool's `ToolResult` row, and, where tool calls are folded into one `ToolGroup` line (focus view), under that line, matched by `tool_use_id`. A plugin tool's result must be a string or content blocks, so the tool answers `#ID PATH`. Its tests are `claude plugin test plugins/show-image`; the plugin interface (function hooks, `Image`) is undocumented, so `test_show_image` runs them against the Claude Code a fresh home installs.

The `clod` launcher mounts a home from `~/.clod/homes/<name>` (or any host path, or with `vol:<name>` the Docker volume `clod-home-<name>`, which Docker fills from the image's `/home/claude`) at `/home/claude` and `.` at `/workspace`, or with `-w` another directory or, as `vol:<name>`, the Docker volume `clod-workspace-<name>` (an option only, never a setting; the `.envrc` is looked up from the workspace, and a volume workspace reads none). Each home keeps its own Claude login (MCP OAuth tokens live in the same file). `~/.clod/shared` is mounted read-only at `/etc/claude-code` (managed settings and CLAUDE.md for every home); until the user creates it (`clod shared new` copies the starter), the repo's `shared/` is mounted there instead. `shared/` is the default set: a statusline with a `settings.json` enabling it (passed as `--settings`, so `managed-settings.json` is left for a user's real policy), and no `CLAUDE.md`, so a user's `~/.clod/shared/CLAUDE.md` holds only their own instructions (`clod shared new` points out one that still repeats `container.md`, and a `managed-settings.json` that still has `statusLine`). Keep it generic; personal instructions belong in the user's own `~/.clod/shared`. Launcher settings (`CLOD_HOME`, `CLOD_IMAGE`, `CLOD_PORTS`, and `CLOD_COMMAND` for what a bare `clod` runs) come from options (`-H`, `-i`, `-P`) or else the host shell environment; container variables come from the nearest direnv-allowed `.envrc` up the tree (only that one file). Launcher settings set by that file are defaults for the shell's, never container variables, and `~/.clod/config` (edited by `clod default KEY VALUE`, with `--reset` to remove one, or by `clod default edit` in the editor, which then names lines clod won't read) holds defaults for both. `CLOD_PORTS` publishes ports (host:container) on the host's 127.0.0.1. Before a run, clod checks their host ports against those other running containers publish: one given with `-P` that is taken stops the run, and one from `CLOD_PORTS` is left out, moved to the next free host port or stops the run, as `CLOD_PORTS_BUSY` (`skip`, the default, `next` or `error`) says. `--docker` mounts the Docker socket (`/var/run/docker.sock`, the same path on Linux, in Colima's VM and in Docker Desktop's) with `--group-add` of its gid as a throwaway container sees it, and passes the project's host path as `CLOD_HOST_WORKSPACE` (none for a volume or scratch workspace); it fails if Docker isn't local. It is deliberately an option only, never a `CLOD_*` setting, so no `.envrc` or config can turn it on. `--scratch` mounts an empty anonymous volume at `/workspace` instead of `.` (the base image makes `/workspace` claude's, which the volume copies), sets `CLOD_SCRATCH`, reads no `.envrc` and skips the workspace refusal; it is an error with `-w`. The bundled `docker` variant supplies the CLI and tells Claude how sibling containers behave. `--clipboard` (setting `CLOD_CLIPBOARD`, `on` or `off`) lets Claude Code's Ctrl+V paste the host clipboard's image: the run starts `clipboard-server.py` (python3, stdlib only) on the host, listening on a free port on 127.0.0.1 (which `host.docker.internal` reaches from Docker Desktop's and Colima's VMs) or on Linux the bridge network's gateway, serving `GET /TOKEN` with the clipboard's image as PNG (or 204), read on each request by `pngpaste` or `osascript` on macOS, `wl-paste` or `xclip` on Linux, or `CLOD_CLIPBOARD_COMMAND`; it exits when clod's process (by then `docker run`) does. The container gets `CLOD_CLIPBOARD_URL`, and the base image's `clipboard.sh`, installed as `xclip` and `wl-paste` in `/usr/local/bin`, fetches from it for the commands Claude Code runs (list types, then read `image/png`), running the real `/usr/bin` tool when the URL is unset. `clod image build [NAME...]` builds the stale images in the chains of the named images (or with none, the current image) without starting a container, `clod image rebuild [NAME...]` rebuilds the whole chains without cache, each image once, pulling a fresh base, and `--skip-build` runs an existing image without checking it; images replaced by any build are pruned. Claude Code and Codex install themselves into the home on first run and self-update. The launcher refuses to mount `$HOME`, a directory above it, `~/.clod` or anything under `~/.clod/homes` as a directory workspace, and `$HOME`, a directory above it, `~/.clod` or `~/.clod/homes` itself as the container home, unless run with `--force`. It checks Docker is reachable before building. `-i clod-NAME` means variant `NAME`, and `-i clod-a.b` the combination `a+b`. The base Dockerfile avoids BuildKit-only syntax, since Homebrew's docker has no buildx and builds with the classic builder; CI checks this.

The command line is strict (`clod help`): clod's options go before the command or anywhere after it up to `--` (`take_option` sets one, for both places), except after a run command, whose arguments are the program's; an option a page doesn't list is accepted and ignored, except `--build`. Unknown options and commands are errors, as are arguments a command doesn't take, and a command's arguments go after it; with no command the default command (`CLOD_COMMAND`, `claude` unless set) runs, and `--` passes the rest to it. The launcher always passes the command to the entrypoint as its first argument. Options only change how a run works; anything that does something else and exits is a command. Commands that manage something are a singular noun, matching its option (`-i`, `-H`, `-w`), with a verb; the bare noun lists (`shared` takes a verb):

- `image` lists the base, the bundled variants, the user's and the images clod built, marking those stale or `in use` (a container uses them); `image show NAME` shows how NAME is built; `image new NAME [FROM]`; `image edit [NAME [FILE]]` opens your variant's Dockerfile (or the `-i`/`CLOD_IMAGE` image's), or FILE beside it (relative, no `.` or `..`), in `$VISUAL`, `$EDITOR` or `vi`, refusing `clod`, a bundled variant (pointing at `image new`) and a combination, and with `--build` (an error with any other command) builds it once the editor exits 0; `image build [NAME...]` and `image rebuild [NAME...]` (above); `image diff NAME` diffs the bundled variant NAME against the user's copy of it (`diff -ru`, status 1 when they differ, like `shared diff`); `image rm NAME...` undoes `image new`, deleting the user's variant directories and the images clod built from them, combinations included (a bundled variant or `clod` has nothing of the user's to delete); `image clean [NAME...]` removes only images clod built, by their `-i` names, or with none the image `-i`/`CLOD_IMAGE` selects (an image others are built on loses only its name); `image prune` removes the stale images clod built, keeping those in use
- `home` lists the homes and their logins; `home new HOME` creates one (a name, path or `vol:NAME`), and a run whose home doesn't exist asks y/N in a terminal before creating it and fails without one, the built-in `default` included; `home cp SRC DEST` copies a home to a new one, either side a name, path or `vol:NAME`, with `rsync -a` in a container of the `clod` image as `claude`; `home mv SRC DEST` is `cp` then deleting the source (a directory to a directory is a rename); both refuse an existing destination, a source or destination a container uses, and `/`, `$HOME` or above, `~/.clod` and `~/.clod/homes` (`off_limits`); `home rm NAME...` removes homes named `NAME` (in `~/.clod/homes`) or `vol:NAME`, refusing paths (a home at a path is a folder the user deletes) and a home a container uses
- `workspace` lists the volume workspaces, marking those a container uses; `workspace rm NAME...` removes them, named `NAME` or `vol:NAME`
- `shared new` creates `~/.clod/shared` from the starter, or if it exists lists the starter's files it lacks or differs on (`--force` replaces it, keeping a backup); `shared diff` shows the diff between the starter and `~/.clod/shared`; `shared edit [FILE]` opens its `CLAUDE.md` or FILE in the editor
- top-level: `env`, `default`, `update` (git pull in clod's checkout, fast-forward only), `install` (links clod onto PATH, and its completion files where bash and zsh load them), `uninstall` (removes only links to its own checkout) and `completion` (prints a tab-completion shim for bash and zsh)

`image rm`, `home rm` and `workspace rm` delete the only copy of their files: in a terminal they list what they'll delete and ask y/N, and `--force` skips the question and is required without a terminal; they refuse an image, home or volume a container uses, even a stopped one. `clod build` and `clod rebuild` are hidden, deprecated aliases of `image build` and `image rebuild`: they print a note naming the new form and are left out of the help, the docs and completion.

The completion functions are `completions/_clod` (zsh, autoloaded from `$fpath`) and `completions/clod.bash` (bash-completion 2): `install` links them where `zsh -lic` and `bash -lic` say those shells load completion from (a zsh with `compinit`, a bash with bash-completion), and prints the `eval "$(clod completion)"` line only when the login shell got neither; `completion` prints the two files wrapped as one shim. Both call the hidden `clod __complete WORDS...`, which exits 1 where a file name belongs (a run command's arguments, `install`'s directory, and a home given as a path: a word with a `/` or starting with `.` or `~`, which no name does) so the shell completes files there and nowhere else. It completes every noun's verbs and their arguments: image names (with `devcontainer` and `devcontainer:NAME` from the current directory's `.devcontainer`, `devcontainer:DIR/` for each subdirectory that has one, and once the word starts `devcontainer:`, the folders and config files in the path typed, a folder ending in `/` taking no space after it) after `-i`, `image show`, `build`, `rebuild` and `clean`, the user's variants after `image rm`, and after `image edit` then that variant's files, those copying a bundled one after `image diff`, homes after `home rm`, homes as the source of `home cp` and `mv`, volume workspace names after `workspace rm`, `new`, `diff` and `edit` after `shared`, then `~/.clod/shared`'s files after `shared edit`, and `edit` among `default`'s keys. It reads the tables, the variant and home directories, the current directory's `.devcontainer` and its subdirectories' and the folders of a `devcontainer:PATH`, never the `.envrc`, and Docker only for volume homes and workspaces and `image clean`'s built images. A candidate can carry a description after a tab (commands, verbs, both forms of each option, setting keys, `--reset`; names and paths have none), which zsh's `_describe` lists beside it, the two forms of an option on one line, and bash's shim drops.

The help comes from tables at the top of `clod`: `command_table` (the commands under the headings `clod help` groups them by, as `NAME|ARGS|SUMMARY`, a noun's verbs as `NOUN VERB` rows), `command_docs` (each command's paragraph), `option_table` (`PAGES|FLAGS|VALUE|DESCRIPTION`, a row per meaning, `PAGES` naming where it shows: `clod` for `clod help`, `run` for the run commands, or commands) and `settings_table`. `clod help` (also `-h` and `--help` before any command) prints the summary, ending "'clod COMMAND -h' shows more about COMMAND."; `clod help COMMAND [VERB]` or `-h`/`--help` anywhere after a command, up to `--`, prints its page, even beside an unknown option or verb (usage forms, with `[OPTIONS]` after the command, or before a run command, paragraph, a noun's verbs, `default`'s keys, its options), except after a run command, whose arguments go to the program. Usage errors end with the page to read: `(see 'clod home rm -h')`, `(see 'clod help claude')` for a run command, or `(see 'clod help')`. `commands`, `nouns` and `noun_verbs` derive from `command_table`, so a new command or verb goes in the two command tables (plus a `cmd_` function and the dispatch), a new option in `parse_args` and `option_table`, and a new setting in `settings_table`; completion and the help pick them up.

On a Linux host, where bind mounts keep host ownership, the launcher builds the base image with `--build-arg CLOD_UID/CLOD_GID` set to the host user's ids (folded into the build hash) so `claude` owns its files, and maps `host.docker.internal` to the host gateway. On macOS the VM's file sharing handles ownership, so `claude` keeps uid 1000.

## Tests

`test/run.sh` is the test suite: shellcheck (`lint`), the launcher's behaviour end to end (`base`), builds without BuildKit (`classic`), each bundled variant (`variant-NAME`; `go+sudo` covers go and sudo, and `docker-socket` the docker variant), the base on another image (`other-base`: an Ubuntu stand-in for a devcontainer image, with a user at claude's uid), and devcontainers (`devcontainer`, which needs the devcontainer CLI, installed in its CI job; `devcontainer-names`, in `base`, needs neither the CLI nor a build). It needs Linux and a Docker it can have to itself, since it builds, replaces and prunes the clod images and mounts the socket into containers, so outside CI it runs only where that Docker is a throwaway, with `--yes`; `test/run.sh lint` runs anywhere. Tests run in order, each line ending with its time and the summary with the run's; before the first variant test it builds the base image, then the selected variants at once. Each run gets a fresh `HOME`, with an empty `default` home, since a run without a terminal won't create one. `test/tab-complete.py` types command lines into real bash and zsh through a pty, for the completion cases that depend on how each shell splits words, with the shim or (`--files`) the files `install` links; with `--list` it prints zsh's listing to check descriptions, and with `--mark` it types `%` after the Tab, showing whether the shell added a space; `test_install` drives `install` and `uninstall` with stand-in shells (`fake_shells`). A new feature gets a `test_*` function in its group's list.

Where it runs:

- CI (`.github/workflows/ci.yml`) runs a few tests per job on fresh GitHub runners, the quick variants together, since every job builds the base image first
- `test/docker.sh run [TEST...]` runs it on any Docker (the CLI's context or `DOCKER_HOST`) in a privileged container (`CLOD_TEST_DOCKER`, default `clod-test`) with its own Docker inside, so the outer Docker's clod images are left alone. The inner Docker keeps its images and build cache in a volume, so later runs are warm; `new` makes it all again for a cold run, and `rm` removes it. It runs on the Docker's architecture (arm64 on Apple silicon)
- `test/incus.sh run [TEST...]` does the same in an incus container (`CLOD_TEST_INCUS`, default `clod-test`, on the incus client's default remote unless named `REMOTE:NAME`) made with a profile that lets Docker run inside (`CLOD_TEST_PROFILE`, default `docker`: `security.nesting` and the mknod and setxattr syscall intercepts, with cloud-init installing docker.io); the container stays between runs, with the same `new` and `rm`
- Both copy in the checkout as it is on disk (tracked files and untracked ones git doesn't ignore), print the result lines as they come, and exit with the suite's status

## Security

The container defines what the agent can reach; within it, the agent runs unrestricted:

- Claude Code runs with `--dangerously-skip-permissions` unless its arguments choose a permission mode, and Codex with `--dangerously-bypass-approvals-and-sandbox`
- The workspace and the whole container home (`~/.clod/homes/<name>`, not the user's own home) are mounted read-write. A new home starts empty and holds only what the user gives it (logins made in the container, copied keys), and all of that is visible to the agent; so are the variables passed in from the `.envrc`
- When a directory workspace is a linked git worktree (`.git` a file with an absolute `gitdir:`), `worktree_mounts` mounts the main repository's common git directory (from the gitdir's `commondir`, read as files: clod never runs git on the workspace) read-write at its host path, with `config`, `hooks` (created if missing), `modules` and, under `extensions.worktreeConfig`, every `worktrees/*/config.worktree` (created empty if missing) read-only, since those make host git run programs. It refuses a common dir that isn't a git directory, is `/` or `$HOME`, or lies under `~/.clod`; a relative gitdir gets a note and no mount
- The container has normal outbound network access and can reach host services via `host.docker.internal`
- With `--clipboard`, the agent can read the host clipboard's image whenever it likes during the run
- With `--docker`, the agent has the Docker socket, which is root on the Docker host (on macOS, the VM, which mounts the user's home folder): it removes the boundary entirely
- `-i devcontainer` builds the project's devcontainer, running its Dockerfile and features on the host's Docker as a variant's build does; nothing in `devcontainer.json` reaches the run
- Claude Code installs via `curl https://claude.ai/install.sh | bash` on first run
- `--rm` discards everything outside the home and workspace mounts after each run

## Docs

`README.md` is the front page: install, first run, and how clod works and what the agent can reach, short enough to read in one go. Everything else is a page in `docs/` linked from its "More" list: `usage.md`, `images.md`, `configuration.md`, `shared-config.md`, `docker-socket.md` (`--docker` and what it gives away), `security.md`, `docker.md` (installing Docker, Linux host notes), `without-clod.md` and `alternatives.md` (other tools compared with clod). A new feature's docs go in the page it belongs to, not the README. `container.md` is the agent's view: what it can see in the container, how the user changes clod on the host, and links to these pages on GitHub; keep it in step with them.

`docs/statusline.svg`, shown in `docs/shared-config.md`, is rendered from the real statusline by `docs/statusline-svg.sh > docs/statusline.svg`: it runs `shared/statusline.sh` on sample input and converts the 16-colour output with `docs/ansi2svg.py`. Regenerate it when the statusline's look changes.
